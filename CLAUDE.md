# RemoteTubeAmplifaier

Контроллер лампового усилителя мощности (УМ): перестройка конденсаторов П-контура и коммутация реле.

## Текущее направление

УМ переводится на ESP32 с веб-мордой для контроля и управления.

- Плата: Waveshare ESP32-S3-ETH (ESP32-S3, 16 МБ flash, 8 МБ PSRAM); Ethernet на W5500, адрес по DHCP, Wi-Fi отключён.
- Сервоприводы: 3 шт. Feetech STS3215 на 12 В (ID 1 — КПЕ, 2 — вариометр, 3 — переключатель БМЗ) на общей полудуплексной шине, 1 Мбит/с, 4096 шагов на оборот. Подключены через адаптер Waveshare Bus Servo Adapter (A): перемычки в A — ESP32 (TX IO47 на `TXD`, RX IO48 на `RXD`), в B — компьютер по USB-C адаптера (`tools/sts-servo.py`). Питание приводов 12 В от отдельного блока. КПЕ и вариометр — ход 180° + 10° запаса (диапазон 0..2162 шага); переключатель БМЗ — 5 положений через 180°.
- Код прошивки: `esp32-backend/esp32-backend.ino` (Arduino, ядро esp32 3.x). Веб-страница — файлы `esp32-backend/data/` (index.html, app.js, style.css) в LittleFS; заливка по USB `tools/upload-www.sh [порт]` или через веб (сервис → «Загрузить файлы»).
- Сборка и прошивка — только через `tools/flash.sh [-p порт] [all|build|firmware|www|monitor]` (по умолчанию all: сборка + прошивка + файлы страницы). Пользователь просил и сам работать через этот скрипт, чтобы он оставался рабочей инструкцией. `arduino-cli` лежит в `~/.local/bin`, плата — `/dev/cu.usbmodem1201`, FQBN `esp32:esp32:esp32s3:FlashSize=16M,PSRAM=opi,CDCOnBoot=cdc`.
- Руководство пользователя: `docs/manual/manual.tex` (LaTeX, xelatex) -> `docs/manual/manual.pdf`, сборка `docs/manual/build.sh` (два прохода, иначе пустое оглавление). Рисунок схемы `docs/manual/scheme.png` — снимок `img/scheme.svg` (headless Chrome, масштаб 2). При изменении устройства или страницы обновлять исходник руководства. PDF собирать в конце работы, а не после каждой правки (указание пользователя 2026-11-21).
- Старая реализация на Python (`py_server/`, `py_client/`, `common/`, Mechaduino + Raspberry Pi) — предыдущее поколение, в рамках новых задач не развивается.

## Договорённости с пользователем (сводка)

Действуют для всех задач, подробности — в разделах задач.

- Работа: сначала план и прямое разрешение, затем правки только согласованных мест; C++17, без лямбд (глобальные правила пользователя). Коммит — только по просьбе, на GitHub не пушить без просьбы.
- Сборка и прошивка — только `tools/flash.sh`. Прошивку и файлы страницы заливать вместе при смене версии API.
- Временные скрипты и результаты исследований не оставлять во временных папках: инструменты — в `tools/`, выводы — в этом файле (просьба пользователя 2026-10-27).
- Документация для пользователя — простым языком «для неподготовленного», в LaTeX со сборкой в PDF (`docs/manual/`).
- В памяти (EEPROM) сервоприводов ничего не хранить: привод может быть заменён. Настройки режима — только в ОЗУ привода (запись при защите EEPROM), данные (точки) — в NVS ESP32.
- Переключатель БМЗ: ноль привода = положение 1, калибровка — кнопка «Привести в ноль», отдельная калибровка каждого из 5 положений не нужна. Путь — кратчайший, счёт оборотов сбрасывается после каждого поворота.
- Передача: запрещена на время перестройки по выбору частоты (и в режиме настройки) и без связи с любым приводом; ручное вращение КПЕ/вариометра в режиме настройки передачу не снимает (настройка под несущей). На странице всегда видно, разрешена ли передача и почему нет.
- Выбор частоты и ручная перестройка — только при включённом прогретом усилителе; сервис (поиск приводов, смена ID, «Привести в ноль») — всегда.
- Без связи с приводом его ручки на странице неактивны; без привода переключателя точку можно сохранить с БМЗ «не задано».
- Автоматическое управление по TCI: при выключенном усилителе и прогреве отслеживать частоту без перестройки; после прогрева применять актуальную ячейку. Режим управления независим от галки настройки.
- ОТЛАДКА: прогрев и охлаждение по 10 с — перед работой с усилителем вернуть 240000 и 300000 (плавный пуск 10 с — не отладочный, не менять).

## Задача 1 — веб-морда с таблицей частот

Постановка: сделать веб-морду, на которой отображается таблица для выбора частот. При выборе частоты меняется положение сервопривода. Пока всё.

Что сделано:

- Веб-страница встроена в прошивку и отдаётся с самой ESP32 (`WebServer`, порт 80).
- Таблица частот с шагом 25 кГц; выбранная частота подсвечивается. При выборе частоты оба сервопривода едут в положения из таблицы.
- Сервоприводы: ID 1 — КПЕ (`cap`), ID 2 — вариометр (`vario`). Управление по протоколу Feetech STS через `Serial1`, протокол реализован в скетче без сторонних библиотек (только запись целевого положения). При старте сервоприводы не двигаются.
- Сеть: IP только по DHCP, свою точку доступа плата не поднимает — это требование. Итоговый вариант — Ethernet на W5500 (плата Waveshare ESP32-S3-ETH), Wi-Fi отключён на уровне компиляции. Переключение — `USE_ETHERNET` в начале скетча (1 = W5500 на SPI через `ETH.h`).

## Задача 2 — режим настройки и показ одного диапазона

Постановка: на веб-странице нужен режим настройки. Выбрана частота (позже она будет приходить по CAT) — пользователь вручную «крутилками» на странице двигает сервоприводы КПЕ и вариометра, находит оптимальную настройку и сохраняет положения сервоприводов для этой частоты. На странице отображается только текущий диапазон.

Что сделано:

- Переключатель «Режим настройки» (состояние хранится на контроллере, общее для всех открытых страниц). В нём для КПЕ и вариометра — ползунок 0..4095 и кнопки шага ±1/±10/±100; сервоприводы едут сразу при изменении.
- «Сохранить» запоминает текущие положения для выбранной частоты; «Сбросить точку» удаляет сохранённую настройку (возврат к значению по умолчанию, сервоприводы не двигаются).
- Несохранённые точки берут положения линейной интерполяцией из таблицы `BANDS` (заглушка).
- Диапазоны: любительские 160–10 м плюс 100 м, 2900–3200 кГц (по просьбе пользователя, 2026-10-16) и 190 м, 1600–1775 кГц (задача 10).
- На странице ряд кнопок диапазонов, показаны частоты только одного; при смене частоты страница сама переходит на её диапазон. Сохранённые частоты помечены зелёной полоской.
- HTTP API (положения в шагах 0..4095):
  - `GET /api/table` — диапазоны и точки `[частота кГц, cap, vario, сохранена 0/1]`;
  - `GET /api/state` — `freq`, `cap`, `vario` (текущие, -1 пока частота не выбиралась), `tuning`, `saved`, `pcap`/`pvario` (положения из таблицы для текущей частоты);
  - `POST /api/select?freq=<кГц>` — выбрать частоту;
  - `POST /api/mode?tuning=0|1` — режим настройки;
  - `POST /api/move?cap=&vario=`, `POST /api/save`, `POST /api/reset` — только в режиме настройки и при выбранной частоте, иначе 409.

Состояние и ограничения:

- Проверено (2026-10-13): плата получает адрес по DHCP; все методы API проверены запросами, сохранение переживает перезагрузку. Страница в браузере мной не проверялась (только синтаксис скрипта).
- Шина приводов (2026-10-26): адаптер Waveshare Bus Servo Adapter (A), перемычки в положении A, разъём UART адаптера `TXD`/`RXD` подключается TX-TX/RX-RX. `SERVO_TX_PIN` = IO47, `SERVO_RX_PIN` = IO48. Эха своей посылки адаптер не возвращает. Питание приводов 12 В (на 14,5 В привод отвечал ошибкой напряжения). Проверено с одним приводом ID 1: опрос, чтение положения, движение с ESP32. README и схема (`docs/scheme.html`, `img/scheme.svg`) обновлены под адаптер. Пины на плате идут на разъём камеры (камера не используется).
- Обратная связь от сервоприводов (реальное положение, ошибки) не читается.
- CAT (частота от трансивера) не реализован. Требование: при выключенном усилителе за трансивером не перестраиваться (задача 11).
- Выбранная частота и режим настройки не сохраняются между перезагрузками. Сеть — Ethernet по DHCP, настройки сети не требуются.
- Ethernet работает на новой плате (W5500 на SPI, Waveshare ESP32-S3-ETH), IP по DHCP.

## Задача 3 — хранение настроек

История: сначала по просьбе пользователя настройки хранились на карте microSD (чтобы переставлять карту между платами), затем пользователь решил отказаться от карты и хранить всё во внутренней flash-памяти ESP32. Код работы с картой удалён.

Что сделано:

- Сохранённые точки лежат во flash-памяти, в NVS (`Preferences`, пространство `tubeamp`, ключ `pts`), записями «частота, КПЕ, вариометр, БМЗ». Переживают перезагрузку и обычную перепрошивку; стираются при «Erase All Flash» или смене разметки памяти.
- Перенос на другую плату — через выгрузку и загрузку таблицы: в режиме настройки под таблицей кнопки «Скачать» и «Загрузить». `GET /api/points.csv` отдаёт файл `частота;КПЕ;вариометр;БМЗ` (строки с `#` — комментарии), `POST /api/points.csv` (тело — текст файла, только в режиме настройки) заменяет все сохранённые точки; файл без единой точки отвергается.
- Точки пользователя (10 шт.) перенесены с карты во flash 2026-10-14 через загрузку таблицы.
- Попутно: вывод лога в USB не блокирует прошивку при закрытом мониторе (`Serial.setTxTimeoutMs(0)`), энергосбережение Wi-Fi выключено (`WiFi.setSleep(false)`) — оба давали задержки отклика.

## Задача 4 — переключатель БМЗ

(Привод на реле заменён третьим сервоприводом — см. задачу 7. Хранение `sw`, API и кнопки остались.)

Постановка: усилитель на базе Р-140. Кроме КПЕ и вариометра нужно переключать БМЗ на переключателе: для каждой ячейки частоты выбирается одно из положений переключателя, его тоже нужно менять в режиме настройки и сохранять.

Что сделано:

- У точки появилось положение БМЗ `sw` (1..`SWITCH_POSITIONS`, 0 — не задано). В режиме настройки на странице ряд кнопок положений; «Сохранить» без выбранного положения БМЗ отказывает — кроме случая, когда привод переключателя (ID 3) не на связи: тогда точка сохраняется с БМЗ «не задано» (решение пользователя 2026-10-26, проверка с одним приводом).
- В записи точки и в файле таблицы четвёртый столбец — БМЗ: `частота;КПЕ;вариометр;БМЗ`. Строки без него читаются как «БМЗ не задано».
- API: в `/api/state` добавлены `sw`, `swmax`, `psw`; `POST /api/move?sw=<n>`; в `/api/table` пятый элемент точки — БМЗ.
- При выборе частоты с незаданным БМЗ все контакты размыкаются и на странице показано «не выбрано» (раньше оставалось положение предыдущей частоты — пользователь принял это за «одно положение на все ячейки»).

- Привод (уточнение пользователя): положение БМЗ выбирается замыканием одного из контактов на блоке БМЗ. В прошивке на каждое положение свой выход GPIO (`SWITCH_PINS`), активен не больше одного; при смене сначала размыкаются все, пауза `SWITCH_PAUSE_MS`, затем замыкается нужный. При старте все контакты разомкнуты, пока не выбрана частота с заданным БМЗ.

- Железо (со слов пользователя): у БМЗ 5 положений. (Позже контакты БМЗ заменены третьим сервоприводом — задача 7.)

Не сделано / открытые вопросы:

- `RELAY_ACTIVE_LEVEL = LOW` — по виду модуля (8 реле, опторазвязка, перемычка JD-VCC) такие включаются низким уровнем; на модуле пользователя не проверено.
- Нет блокировки переключения БМЗ во время передачи (сигнала PTT в прошивке нет).
- Проверено на плате (2026-10-13): выбор, отказ без БМЗ, сохранение, чтение после перезагрузки; по логу — что выбирается нужный GPIO. Модуль реле не подключён, уровни на выводах не измерялись. Страница в браузере мной не проверялась.

## Задача 5 — сервисный режим смены ID сервоприводов

Постановка: в веб-форме и прошивке сделать сервисный режим для смены ID сервоприводов.

Что сделано:

- На странице внизу раскрывающийся блок «Сервис: ID сервоприводов»: «Найти приводы» (опрос ID 0..253 с чтением положения, около 1,3 с) и «Сменить ID: с … на …».
- Прошивка научилась читать ответы приводов: `stsTransfer()` при `wantReply` ждёт ответ до `STS_REPLY_TIMEOUT_MS` (5 мс), пропускает эхо своей посылки (схема с резистором на общую линию) и проверяет контрольную сумму. Есть `stsPing()`, `stsReadPosition()` (регистр 56).
- Смена ID: проверка, что старый ID отвечает, а новый свободен; затем снятие защиты EEPROM (регистр 55 = 0), запись ID (регистр 5), защита на новом ID (55 = 1), проверка ответа на новом ID.
- API: `POST /api/servo/scan` -> `{"servos":[{"id","pos"}]}`; `POST /api/servo/id?from=&to=`.
- Команды движения ответа по-прежнему не ждут (на скорость отклика не влияет).

Проверено: на плате без приводов — опрос возвращает пустой список, смена ID отвечает понятными ошибками; разбор ответа проверен на компьютере на имитации ответов (с эхом и без, с неверной контрольной суммой). С реальными приводами не проверялось; адреса регистров взяты из протокола Feetech STS.

## Задача 6 — модуль реле: включение, прогрев, анодное, PTT

(Плавный пуск и вход «анодное есть» убраны — см. задачу 10.)

Постановка: модуль на 8 реле с опторазвязкой (входы IN1..IN8, перемычка JD-VCC) использовать для: 1) включения УМ; 2) замыкания плавного пуска через 5 с после включения, после чего все функции заблокированы 3 минуты (прогрев ламп); 3) пяти реле БМЗ (замкнуто только одно); 4) разрешения/запрета PTT (после прогрева; запрет при срабатывании защиты и отсутствии анодного); 5) включения анодного после прогрева. Веб-страница показывает процессы: этап включения, найдены ли сервоприводы, состояние PTT, анодного и т.п.

Что сделано:

- Реле (все включаются `RELAY_ACTIVE_LEVEL = LOW`): питание 220 В IO38 (реле 1), плавный пуск IO39 (реле 2), реле 3 — PTT трансивера IO40 (задача 9), реле 4..7 свободны (БМЗ на сервоприводе, задача 7), PTT усилителя IO17 (реле 8, см. задачу 8), анодное IO18 — реле 1 второго модуля на 4 реле (решение пользователя; реле 2..4 этого модуля свободны).
- Входы от усилителя (`INPUT_PULLUP`, активный уровень LOW, подавление дребезга 50 мс): защита IO43. (Вход «наличие анодного» удалён — задача 10.)
- Последовательность: «Включить» -> реле питания -> через 5 с плавный пуск -> прогрев 180 с (выбор частоты и ручное управление отвечают 409) -> реле анодного -> PTT разрешается, когда есть сигнал анодного и нет защиты. «Выключить» в любой момент: PTT, анодное, плавный пуск, питание.
- PTT запрещён, пока: усилитель выключен или греется; защита сработала (защёлкивается до кнопки «Сбросить защиту», сброс возможен только при неактивном сигнале); нет сигнала анодного (первые 5 с после включения — «ожидание»); идёт поворот переключателя БМЗ или он не встал в положение (задача 7). Ручное вращение КПЕ и вариометра в режиме настройки PTT не снимает — настройка идёт под несущей; перестройка по выбору частоты снимает (задача 11).
- Сервоприводы опрашиваются раз в секунду (чтение положения ID 1 и 2): страница показывает реальное положение или «нет связи».
- Страница: блок состояния вверху — этап с обратным отсчётом, индикаторы (питание, плавный пуск, анодное реле/сигнал, PTT, защита, КПЕ, вариометр), причина запрета PTT, кнопки «Включить/Выключить» (с подтверждением) и «Сбросить защиту». Во время прогрева таблица и ручное управление неактивны.
- API: `POST /api/power?on=0|1`, `POST /api/protection/reset`; в `/api/state` поля `amp` (off/softstart/warmup/ready), `remain`, `power`, `soft`, `anode`, `anodeOk`, `protect`, `protectLatched`, `ptt`, `pttReason`, `servoCap`, `servoVario`.
- После перезагрузки ESP32 все реле выключены, усилитель выключается.
- Вёрстка (по просьбе пользователя): кнопка «Включить/Выключить» слева в блоке состояния; на компьютере (от 900 px) две колонки — слева состояние и режим настройки, справа таблица частот; на телефоне (до 600 px) одна колонка: состояние, таблица, настройка, сервис; крупные кнопки под палец. Проверено снимками headless Chrome с платы (1400 px и 390 px).

Открытые вопросы к пользователю:

- Как устроены сигналы защиты и наличия анодного (контакт, оптрон, уровень) — сейчас предположение: замыкание на GND = активен.
- Что делать с анодным при срабатывании защиты (сейчас остаётся включённым, снимается только PTT).
- Пины на ESP32-S3-ETH: GPIO33–37 заняты PSRAM (OPI), их использовать нельзя; пины реле/входов/сервоприводов переназначены — см. задачу 17.

## Задача 7 — переключатель БМЗ на третьем сервоприводе

Постановка: БМЗ на реле больше нет, вместо него третий сервопривод вращает переключатель. Шаг 360/5 — 5 положений; ограничителей нет, вращение в любую сторону, кратчайшим путём или по кругу. Положение выбирается кнопками на странице и сохраняется для частоты, прошивка сама ставит привод в одно из 5 положений.

Решения пользователя: ID привода 3; калибровка положения 1 через веб; PTT снимается на всё время поворота.

Что сделано:

- (Устарело, см. задачу 12: шаговый режим заменён многооборотным.) Привод ID 3 переводится в шаговый режим STS (регистр 33 = 3, запись в EEPROM только если режим другой). Положение n -> шаг `switchOffset + (n-1)*4096/5` (0, 819, 1638, 2458, 3277 + смещение). Перед поворотом читается текущее положение (с декодированием знака в 15-м бите и приведением к 0..4095), считается кратчайшая разница ±2048 и отправляется относительное перемещение — ошибка не накапливается.
- Поворот неблокирующий: `updateSwitch()` раз в 50 мс читает положение; встал (допуск 20 шагов) — PTT возвращается; нет за 4 с или привод не отвечает — `switchFailed`, PTT запрещён до успешного поворота.
- (Устарело, см. задачу 12: калибровка — кнопка «Привести в ноль».) Калибровка в сервисном блоке: ползунок положения привода 0..4095 (`POST /api/switch/move?pos=`, поворот кратчайшим путём; добавлен по просьбе пользователя — вручную привод не провернуть), кнопки ±1/±10/±100 (`POST /api/switch/jog?steps=`) и «Запомнить как положение 1» (`POST /api/switch/calibrate`); смещение в NVS, ключ `swofs`.
- Страница: индикатор «Переключатель» (положение / поворот / не встал / нет связи); в `/api/state` поля `servoSwitch`, `swMoving`, `swFailed`, `swOffset`.
- Реле 3..7 модуля на 8 реле освобождены (БМЗ на сервоприводе). Лямбда в `sendState()` заменена функцией `jsonBool()` (правило пользователя: без лямбд в C++).

Проверено: математика положений и кратчайшего пути — на компьютере; на плате без привода — понятные ошибки, PTT блокируется. С реальным приводом не проверялось: шаговый режим, формат положения в нём и направление вращения требуют проверки.

## Задача 8 — PTT через ESP32 и охлаждение перед выключением

Постановка: управление PTT завести в ESP32 и учесть таймаут после последней передачи в эфир. Если выбрали «Выключить», а с последней передачи прошло меньше 5 минут, усилитель не выключается, но показывается кнопка «Выключить без охлаждения».

Что сделано:

- PTT трансивера — вход IO44 (`INPUT_PULLUP`, активен LOW, дребезг 5 мс). Реле 8 теперь «PTT усилителя»: замкнуто, пока вход PTT активен и `pttBlockReason()` пуст (прогрев окончен, есть анодное, нет защиты, переключатель БМЗ встал).
- Последняя передача — последний момент, когда реле 8 было замкнуто или шла передача с веб-страницы (`lastTxMs`, `txHappened`; веб-передача добавлена после жалобы пользователя: нажал «Передача», а охлаждения не было — без подключённых PTT/датчика анодного реле 8 не замыкалось); после перезагрузки ESP32 считается, что передачи не было.
- `POST /api/power?on=0` при `cooldownSeconds() > 0` (меньше `COOLDOWN_MS` = 5 мин с передачи) отвечает 409; `&force=1` выключает сразу. Страница после отказа показывает кнопку «Выключить без охлаждения» и отсчёт охлаждения.
- Вариант, когда при «Выключить» во время охлаждения снимается анодное и усилитель выключается сам по окончании, предлагался; пользователь на вопрос не ответил, сделано по его постановке (просто не выключать).
- `/api/state`: `ptt` (реле 8 замкнуто), `pttAllowed`, `pttReason`, `txReq` (вход PTT), `lastTx` (секунд с передачи, -1 — не было), `cooldown` (секунд до конца охлаждения).
- Задержка PTT: цикл прошивки при отсутствующих приводах занят опросом до ~15 мс раз в секунду, плюс 5 мс дребезга и время срабатывания реле — задержку передачи на трансивере лучше выставить с запасом.

Проверено: на плате — поля состояния и выключение без передачи; логика замыкания PTT и отсчёта охлаждения — на компьютере с имитацией времени. Вход PTT и реле на железе не проверялись.

## Задача 11 — запрет передачи при перестройке, индикатор, ручки без связи

Постановка (2026-10-26): в режиме работы перестройка идёт по выбору частоты (кнопкой, в будущем по CAT) — пока приводы перестраиваются, передача недоступна. В режиме настройки КПЕ и вариометр крутятся вручную под несущей, передачу это не блокирует. На странице нужен индикатор, возможна ли передача. Ручки привода, которого нет на связи, неактивны.

Что сделано:

- Выбор частоты (`/api/select`, в том числе в режиме настройки — решение пользователя) запускает `retuneServos()`: флаги перестройки КПЕ и вариометра, PTT снимается (пауза `PTT_RELEASE_MS`, если был замкнут). `updateRetune()` раз в `SERVO_CHECK_MS` (50 мс) читает положения; в пределах `SERVO_TOLERANCE` (20 шагов) — встал; за `SERVO_MOVE_TIMEOUT_MS` (5 с) не встал или не отвечает — `failed`, PTT запрещён до следующей перестройки. Ручное движение (`/api/move` с `cap`/`vario`) перестройку отменяет (`cancelRetune()`).
- Нет связи с приводом КПЕ или вариометра (опрос раз в секунду) — PTT запрещён (решение пользователя). `pollServos()` после опроса вызывает `updatePtt()`.
- Запрет PTT (по порядку): выключен; прогрев; защита; перестройка КПЕ и вариометра; нет связи с КПЕ / вариометром; КПЕ / вариометр не встал; поворот БМЗ; БМЗ не встал / нет связи.
- `/api/state`: `capMoving`, `capFailed`, `varioMoving`, `varioFailed` (версия API не менялась).
- Страница: плашка под кнопками «Передача разрешена» / «Передача запрещена: причина» / «Идёт передача», видна всегда; индикаторы КПЕ и вариометра — положение / перестройка / не встал / нет связи. Без связи с приводом неактивны его ползунок и кнопки шага, кнопки БМЗ и калибровка переключателя в сервисе.

- Выбор частоты (`/api/select`) и ручная перестройка (`/api/move`) только при включённом усилителе: выключен — 409 «усилитель выключен», прогрев — 409 как раньше (решение пользователя: для настройки нужно включать усилитель). На странице кнопки частот и панель настройки неактивны, пока усилитель не готов. Сервис (поиск, смена ID, калибровка переключателя) доступен всегда.
- Для будущего CAT (требование пользователя): пока усилитель выключен, перестройка за трансивером не ведётся — частота только запоминается; при включении приводы перестраиваются на неё (можно во время прогрева — PTT всё равно запрещён).

Проверено на плате с одним приводом (ID 1): перестройка по выбору частоты, снятие флага по прибытии (~1,5 с), «не встал» у отсутствующего вариометра через 5 с; страница — снимком headless Chrome. Причины запрета при включённом усилителе на плате не смотрелись.

## Задача 12 — переключатель БМЗ в многооборотном режиме, потеря связи с приводами

Постановка (2026-10-27): привод переключателя работал нелогично, особенно 1 -> 2 и обратно; при пропадании питания во время поворота калибровка не должна слетать; в памяти привода ничего не хранить (привод может быть заменён); счёт оборотов не должен расти бесконечно.

Исследовано с компьютера (адаптер в положении B, утилита `tools/sts-servo.py`) на STS3215 ID 3:

- Шаговый режим (33 = 3): регистр положения 56 показывает не угол, а остаток текущего перемещения (817 -> 2, со знаком в 15-м бите), в покое около 0. Прошивка считала его углом — отсюда неверные повороты и таймауты. Первую команду после подачи питания привод проигнорировал.
- Многооборотный режим: 33 = 0 и ограничения угла 9 = 11 = 0. Цель (42) со счётом оборотов, знак в 15-м бите; положение (56) — угол 0..4095. Через ноль едет кратчайшим путём.
- Счёт оборотов: снятие и подача удержания (40) его не сбрасывают; запись цели при снятом удержании тоже (привод потом уезжает на оборот). Сбрасывает только выключение питания: после него цель = 0, удержание = 0, счёт = углу.
- Пропадание 12 В посреди вращения: угол до 3015, после 3014 — датчик абсолютный, положение не теряется. Режим и ограничения в EEPROM сохраняются.
- У привода ID 3 регистр 31 (собственная поправка) = 85, прошивка его не трогает.

Дальнейшие проверки с компьютера (2026-10-27):

- Окно счёта -1..+2 оборота (первая версия) не годится: при переключении 1->2->3->4->5->1 по кругу счёт растёт на оборот за круг, у края окна привод уходит по кругу назад (жалоба пользователя: «5 -> 1 долго»).
- Счёт сбрасывается переходом в шаговый режим и обратно (33: 3 -> 0): после него счёт = углу, вал не дёргается, но привод снимает удержание (40 = 0).
- Записи в регистры EEPROM при защите (55 = 1) действуют только до выключения питания привода: записали режим 3 и ограничение 4095 при 55 = 1, после выключения 12 В вернулись прежние. EEPROM привода ID 3 возвращён к заводским значениям (режим 0, ограничения 0..4095).

Что сделано в прошивке:

- `ensureSwitchMultiTurn()` перед каждым поворотом проверяет режим 0 и ограничения 0/0 и при необходимости пишет их при защите EEPROM — только в ОЗУ привода (решение пользователя: в памяти привода ничего не хранить, привод может быть заменён). После пропадания питания привода настройка восстанавливается сама.
- `moveSwitchTo()`: счёт оборотов = угол, если удержание выключено (питание подали или счёт сброшен), иначе последняя цель, поправленная на угол; новая цель = счёт + кратчайшая разница (±2048). `setServoPosition()` кодирует отрицательную цель.
- `updateSwitch()`: привод встал (допуск 20 шагов) -> `resetSwitchTurns()`: режим 3 -> 0 в ОЗУ, затем цель = кратчайший путь от угла к нужному углу (возвращает удержание и доводит последние шаги допуска). Счёт всегда в пределах одного оборота, путь всегда кратчайший, в том числе 5 -> 1 через ноль. PTT разрешается после сброса.
- Калибровка (решение пользователя): вместо смещения положения 1 — кнопка «Привести в ноль» (`POST /api/switch/zero`, работает и при выключенном усилителе). Ноль привода = положение 1, положения фиксированы: 0, 819, 1638, 2458, 3277 (шаг позже изменён на 180°, см. задачу 14); переключатель выставляется механически под ноль привода. Смещение `swofs` в NVS, ползунок, кнопки ±1/±10/±100, `/api/switch/jog`, `/move`, `/calibrate` и поле `swOffset` удалены (ключ `swofs` мог остаться в NVS — не читается). `WWW_API_VERSION` / `API_VERSION` = 3.
- Нет связи с приводом переключателя — PTT запрещён всегда (раньше только при неудачном повороте).
- Привод снова на связи (`pollServos()`: было -1, стало >= 0) при включённом усилителе и выбранной частоте — сам перестраивается в положение текущей частоты: КПЕ/вариометр через `startRetune()` (цель отправляется всегда, даже прежняя), переключатель через `moveSwitchTo()`.
- `tools/sts-servo.py`: команды `multiturn ID` и `resetturns ID` (только в ОЗУ привода).

Проверено на плате (2026-10-27), приводы ID 2 и 3, КПЕ не подключён:
- «Привести в ноль»: привод с заводским EEPROM — прошивка включила многооборотный режим в ОЗУ, 405 -> 0.
- Круг 1->2->3->4->5->1 три раза подряд: каждый переход ~0,9 с (1/5 оборота, шаг позже изменён на 180° — задача 14), 5 -> 1 вперёд через ноль, счёт перед каждым поворотом равен углу, «не встал» нет.
- Выключение 12 В на ~5 с при включённом усилителе: «нет связи», после включения — `link restored`, режим в ОЗУ восстановлен, вариометр и переключатель перестроены в прежние положения (1148, 1636).
- Не видно вживую: причины запрета «нет связи с переключателем» / «перестройка» — в плашке перекрыты причиной «нет связи с приводом КПЕ» (КПЕ не подключён).

## Задача 14 — шаг переключателя БМЗ 180°, обратное вращение, абсолютная цель привода

Постановка (2026-11-09): фактический шаг переключателя — 180° (пол-оборота привода), а не 360°; вращение мотора при переключении идёт в обратную сторону. Пользователь выбрал вариант с абсолютными целями от нуля (вариант 2 из предложения), а не минимальную правку.

Почему нельзя было поменять только константу: старый код после каждого поворота сбрасывал счёт оборотов к углу и считал, что после N полных оборотов угол возвращается к стартовому. При шаге 180° пять положений занимают 2,5 оборота, поэтому угол привода даёт положение только с точностью до чётности (1, 3, 5 — на 0°, 2 и 4 — на 180°), а «докрутить до 0°» после обрыва перестаёт быть верным.

Что сделано в прошивке (`esp32-backend/esp32-backend.ino`):

- `SWITCH_STEPS_PER_POS` = 2048 (180°), добавлен `SWITCH_DIRECTION` = -1 (обратное вращение). Направление положений задаётся знаком `switchGoalForPos()`.
- Цель привода — абсолютный счёт шагов от нуля: `switchBase` (счёт при положении 1) + `(pos-1)*2048*SWITCH_DIRECTION`. Пять положений укладываются в 0..2 оборота, счёт не растёт и не сбрасывается. Повторная отправка цели вал не двигает, прерванный поворот продолжается, а не начинается заново (идемпотентно).
- `moveSwitchToPos(pos)` заменил `moveSwitchByTurns()`, `startSwitchAngleMove(angle)` заменил `moveSwitchTo()` (только «Привести в ноль»). `readSwitchState(angle, goal, counterValid)` заменил `readSwitchGoal()`/`prepareSwitch()`. `finishSwitchMove()` заменил `onSwitchArrived()`; `resetSwitchTurns()` и `switchAngleNearZero()` удалены.
- Восстановление после появления связи: `busy=0` — переключатель физически на положении из NVS, `switchBase` считается по текущему углу; `busy=1` и удержание включено (привод питания не терял) — прошлая цель = абсолютный адрес `to`, доезжаем до неё; `busy=1` и удержание выключено (привод обесточивался посреди поворота) — абсолютное положение восстановить нельзя: PTT запрещён, `switchBaseValid = false`, на странице «нужно «Привести в ноль»».
- «Привести в ноль»: вал едет к углу 0 кратчайшим путём, `switchBase` = отправленная цель; положение 1 известно снова.
- `/api/state`: поле `swRecovering` заменено на `swZero` (`false` — ноль неизвестен). `WWW_API_VERSION` / `API_VERSION` не менялись (поле добавлено, страница и прошивка заливаются вместе).
- Страница (`app.js`): индикатор переключателя показывает «нужно «Привести в ноль»», когда `swZero === false`.

Документация: README.md (таблица железа, калибровка, раздел «НОВАЯ ЛОГИКА БМЗ»), README.en.md (шаг 180°), `docs/manual/manual.tex` (шаг 180°, абзац про пропадание питания приводов). `manual.pdf` в этом окружении не пересобирался — xelatex не установлен, собрать `docs/manual/build.sh` на машине с TeX.

Проверено: сборка `tools/flash.sh build`. На железе не проверялось (плата не подключена). После прошивки нужно: «Привести в ноль», затем переключить 1->2->3->4->5->4->3->2->1 и убедиться, что направление правильное и каждый переход — пол-оборота.

## Справка: HaLow-модуль TX-AH на T-Halow

Разобрано по примерам и документации LilyGO (github.com/Xinyuan-LilyGO/T-Halow), на железе не проверялось. В проекте пока не используется.

- У TX-AH две взаимоисключающие прошивки (на съёмной микросхеме Flash):
  - `...-usb.bin` — режим AT: ESP32 управляет модулем по UART (`Serial1`, 115200, RX = GPIO4, TX = GPIO5) и обменивается данными с парной платой по радио;
  - `...-WNB.bin` — сетевой мост RJ45 <-> HaLow <-> RJ45; настраивается по micro-USB, ESP32 в обмене не участвует.
- Отправка: `AT+TXDATA=<длина>`, дождаться `OK`, затем послать ровно `<длина>` байт: 14 байт Ethernet-заголовка (MAC получателя, MAC отправителя, тип) + полезные данные.
- Приём: модуль выдаёт строку `+RXDATA:...`, после перевода строки — тот же кадр (14 байт заголовка + данные). Пример `TX_AH_Rx00p_STA` пропускает 15 символов после начала перевода строки.
- Состояние связи: `AT+CONN_STATE` -> `+CONNECTED` / `+DISCONNECT`; уровень сигнала: `AT+RSSI=1`.
- Сопряжение: одна плата AP, другая STA (`AT+MODE=AP|STA` или переключатель на плате), затем `AT+PAIR=1` на обеих или кнопка PAIR.
- Занятые на плате GPIO: 4/5 — UART к TX-AH, 39/40/41/42 — SD-карта, 38 — светодиод, 6/7 — I2C.
