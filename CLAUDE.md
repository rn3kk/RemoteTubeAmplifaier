# RemoteTubeAmplifaier

Контроллер лампового усилителя мощности (УМ): перестройка конденсаторов П-контура и коммутация реле.

## Текущее направление

УМ переводится на ESP32 с веб-мордой для контроля и управления.

- Плата: сейчас LilyGO T-Halow (ESP32-S3); позже пользователь заменит её на плату ESP32-S3 с Ethernet («s3-eth», точная модель не названа).
- Сервоприводы: 2 шт. Feetech STS3215 (КПЕ и вариометр) на общей полудуплексной UART-шине, 1 Мбит/с, 4096 шагов на оборот.
- Код прошивки: `esp32-backend/esp32-backend.ino` (Arduino, ядро esp32 3.x).
- Сборка: `arduino-cli compile --fqbn esp32:esp32:esp32s3:FlashSize=16M,PSRAM=opi,CDCOnBoot=cdc esp32-backend` (`arduino-cli` лежит в `~/.local/bin`). Плата видна как `/dev/ttyACM0`.
- Старая реализация на Python (`py_server/`, `py_client/`, `common/`, Mechaduino + Raspberry Pi) — предыдущее поколение, в рамках новых задач не развивается.

## Задача 1 — веб-морда с таблицей частот

Постановка: сделать веб-морду, на которой отображается таблица для выбора частот. При выборе частоты меняется положение сервопривода. Пока всё.

Что сделано:

- Веб-страница встроена в прошивку и отдаётся с самой ESP32 (`WebServer`, порт 80).
- Таблица частот с шагом 25 кГц; выбранная частота подсвечивается. При выборе частоты оба сервопривода едут в положения из таблицы.
- Сервоприводы: ID 1 — КПЕ (`cap`), ID 2 — вариометр (`vario`). Управление по протоколу Feetech STS через `Serial1`, протокол реализован в скетче без сторонних библиотек (только запись целевого положения). При старте сервоприводы не двигаются.
- Сеть: IP только по DHCP, свою точку доступа плата не поднимает — это требование. Целевой вариант — Ethernet; пока плата T-Halow, по решению пользователя временно используется Wi-Fi-клиент; `WIFI_SSID`/`WIFI_PASS` лежат в `esp32-backend/secrets.h`, файл в `.gitignore` и не коммитится (репозиторий уходит на GitHub). Переключение — `USE_ETHERNET` в начале скетча (1 = W5500 на SPI через `ETH.h`).

## Задача 2 — режим настройки и показ одного диапазона

Постановка: на веб-странице нужен режим настройки. Выбрана частота (позже она будет приходить по CAT) — пользователь вручную «крутилками» на странице двигает сервоприводы КПЕ и вариометра, находит оптимальную настройку и сохраняет положения сервоприводов для этой частоты. На странице отображается только текущий диапазон.

Что сделано:

- Переключатель «Режим настройки» (состояние хранится на контроллере, общее для всех открытых страниц). В нём для КПЕ и вариометра — ползунок 0..4095 и кнопки шага ±1/±10/±100; сервоприводы едут сразу при изменении.
- «Сохранить» запоминает текущие положения для выбранной частоты; «Сбросить точку» удаляет сохранённую настройку (возврат к значению по умолчанию, сервоприводы не двигаются).
- Несохранённые точки берут положения линейной интерполяцией из таблицы `BANDS` (заглушка).
- На странице ряд кнопок диапазонов, показаны частоты только одного; при смене частоты страница сама переходит на её диапазон. Сохранённые частоты помечены зелёной полоской.
- HTTP API (положения в шагах 0..4095):
  - `GET /api/table` — диапазоны и точки `[частота кГц, cap, vario, сохранена 0/1]`;
  - `GET /api/state` — `freq`, `cap`, `vario` (текущие, -1 пока частота не выбиралась), `tuning`, `saved`, `pcap`/`pvario` (положения из таблицы для текущей частоты);
  - `POST /api/select?freq=<кГц>` — выбрать частоту;
  - `POST /api/mode?tuning=0|1` — режим настройки;
  - `POST /api/move?cap=&vario=`, `POST /api/save`, `POST /api/reset` — только в режиме настройки и при выбранной частоте, иначе 409.

Состояние и ограничения:

- Проверено на T-Halow (2026-10-13): Wi-Fi-вариант прошит, плата получает адрес по DHCP; все методы API проверены запросами, сохранение переживает перезагрузку. Страница в браузере мной не проверялась (только синтаксис скрипта).
- Сервоприводы пока не подключены: движение, пины шины и схема согласования не проверены. `SERVO_TX_PIN`/`SERVO_RX_PIN` (IO21/IO47) выбраны по надписям гребёнки на фото; на плате они же идут на разъём камеры (камера не используется).
- Обратная связь от сервоприводов (реальное положение, ошибки) не читается.
- CAT (частота от трансивера) не реализован.
- Выбранная частота и режим настройки не сохраняются между перезагрузками. Настройки сети (Wi-Fi) задаются в `secrets.h`.
- Ethernet-вариант только собирается. Штатный RJ45 на T-Halow (V1.0 24-08-23) ESP32 недоступен: он идёт через RMII-PHY IP101GRI к HaLow-модулю TX-AH, а у ESP32-S3 нет Ethernet-MAC. Пины `ETH_*` в скетче — заглушка, уточнить под новую плату.

## Задача 3 — хранение настроек

История: сначала по просьбе пользователя настройки хранились на карте microSD (чтобы переставлять карту между платами), затем пользователь решил отказаться от карты и хранить всё во внутренней flash-памяти ESP32. Код работы с картой удалён.

Что сделано:

- Сохранённые точки лежат во flash-памяти, в NVS (`Preferences`, пространство `tubeamp`, ключ `pts`), записями «частота, КПЕ, вариометр, БМЗ». Переживают перезагрузку и обычную перепрошивку; стираются при «Erase All Flash» или смене разметки памяти.
- Перенос на другую плату — через выгрузку и загрузку таблицы: в режиме настройки под таблицей кнопки «Скачать» и «Загрузить». `GET /api/points.csv` отдаёт файл `частота;КПЕ;вариометр;БМЗ` (строки с `#` — комментарии), `POST /api/points.csv` (тело — текст файла, только в режиме настройки) заменяет все сохранённые точки; файл без единой точки отвергается.
- Точки пользователя (10 шт.) перенесены с карты во flash 2026-10-14 через загрузку таблицы.
- Попутно: вывод лога в USB не блокирует прошивку при закрытом мониторе (`Serial.setTxTimeoutMs(0)`), энергосбережение Wi-Fi выключено (`WiFi.setSleep(false)`) — оба давали задержки отклика.

## Задача 4 — переключатель БМЗ

Постановка: усилитель на базе Р-140. Кроме КПЕ и вариометра нужно переключать БМЗ на переключателе: для каждой ячейки частоты выбирается одно из положений переключателя, его тоже нужно менять в режиме настройки и сохранять.

Что сделано:

- У точки появилось положение БМЗ `sw` (1..`SWITCH_POSITIONS`, 0 — не задано). В режиме настройки на странице ряд кнопок положений; «Сохранить» без выбранного положения БМЗ отказывает.
- В записи точки и в файле таблицы четвёртый столбец — БМЗ: `частота;КПЕ;вариометр;БМЗ`. Строки без него читаются как «БМЗ не задано».
- API: в `/api/state` добавлены `sw`, `swmax`, `psw`; `POST /api/move?sw=<n>`; в `/api/table` пятый элемент точки — БМЗ.
- При выборе частоты с незаданным БМЗ все контакты размыкаются и на странице показано «не выбрано» (раньше оставалось положение предыдущей частоты — пользователь принял это за «одно положение на все ячейки»).

- Привод (уточнение пользователя): положение БМЗ выбирается замыканием одного из контактов на блоке БМЗ. В прошивке на каждое положение свой выход GPIO (`SWITCH_PINS`), активен не больше одного; при смене сначала размыкаются все, пауза `SWITCH_PAUSE_MS`, затем замыкается нужный. При старте все контакты разомкнуты, пока не выбрана частота с заданным БМЗ.

- Железо (со слов пользователя): у БМЗ 5 положений, контакты замыкает модуль реле с опторазвязкой «для Arduino». `SWITCH_PINS` = IO9..IO13.

Не сделано / открытые вопросы:

- `SWITCH_ACTIVE_LEVEL = LOW` — предположение (такие модули обычно включаются низким уровнем); на модуле пользователя не проверено. Пины IO9..IO13 заняты под W5500 при `USE_ETHERNET 1`, на новой плате переназначить.
- Нет блокировки переключения БМЗ во время передачи (сигнала PTT в прошивке нет).
- Проверено на плате (2026-10-13): выбор, отказ без БМЗ, сохранение, чтение после перезагрузки; по логу — что выбирается нужный GPIO. Модуль реле не подключён, уровни на выводах не измерялись. Страница в браузере мной не проверялась.

## Задача 5 — сервисный режим смены ID сервоприводов

Постановка: в веб-форме и прошивке сделать сервисный режим для смены ID сервоприводов.

Что сделано:

- На странице внизу раскрывающийся блок «Сервис: ID сервоприводов»: «Найти приводы» (опрос ID 0..253 с чтением положения, около 1,3 с) и «Сменить ID: с … на …».
- Прошивка научилась читать ответы приводов: `stsTransfer()` при `wantReply` ждёт ответ до `STS_REPLY_TIMEOUT_MS` (5 мс), пропускает эхо своей посылки (схема с резистором на общую линию) и проверяет контрольную сумму. Есть `stsPing()`, `stsReadPosition()` (регистр 56).
- Смена ID: проверка, что старый ID отвечает, а новый свободен; затем снятие защиты EEPROM (регистр 55 = 0), запись ID (регистр 5), защита на новом ID (55 = 1), проверка ответа на новом ID.
- API: `POST /api/servo/scan` -> `{"servos":[{"id","pos"}]}`; `POST /api/servo/id?from=&to=`.
- Команды движения ответа по-прежнему не ждут (на скорость отклика не влияет).

Проверено: на плате без приводов — опрос возвращает пустой список, смена ID отвечает понятными ошибками; разбор ответа проверен на компьютере на имитации ответов (с эхом и без, с неверной контрольной суммой). С реальными приводами не проверялось; адреса регистров взяты из протокола Feetech STS.

## Справка: HaLow-модуль TX-AH на T-Halow

Разобрано по примерам и документации LilyGO (github.com/Xinyuan-LilyGO/T-Halow), на железе не проверялось. В проекте пока не используется.

- У TX-AH две взаимоисключающие прошивки (на съёмной микросхеме Flash):
  - `...-usb.bin` — режим AT: ESP32 управляет модулем по UART (`Serial1`, 115200, RX = GPIO4, TX = GPIO5) и обменивается данными с парной платой по радио;
  - `...-WNB.bin` — сетевой мост RJ45 <-> HaLow <-> RJ45; настраивается по micro-USB, ESP32 в обмене не участвует.
- Отправка: `AT+TXDATA=<длина>`, дождаться `OK`, затем послать ровно `<длина>` байт: 14 байт Ethernet-заголовка (MAC получателя, MAC отправителя, тип) + полезные данные.
- Приём: модуль выдаёт строку `+RXDATA:...`, после перевода строки — тот же кадр (14 байт заголовка + данные). Пример `TX_AH_Rx00p_STA` пропускает 15 символов после начала перевода строки.
- Состояние связи: `AT+CONN_STATE` -> `+CONNECTED` / `+DISCONNECT`; уровень сигнала: `AT+RSSI=1`.
- Сопряжение: одна плата AP, другая STA (`AT+MODE=AP|STA` или переключатель на плате), затем `AT+PAIR=1` на обеих или кнопка PAIR.
- Занятые на плате GPIO: 4/5 — UART к TX-AH, 39/40/41/42 — SD-карта, 38 — светодиод, 6/7 — I2C.
