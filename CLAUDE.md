# RemoteTubeAmplifaier

Контроллер лампового усилителя мощности (УМ): перестройка конденсаторов П-контура и коммутация реле.

## Текущее направление

УМ переводится на ESP32 с веб-мордой для контроля и управления.

- Плата: сейчас LilyGO T-Halow (ESP32-S3); позже пользователь заменит её на плату ESP32-S3 с Ethernet («s3-eth», точная модель не названа).
- Сервоприводы: 2 шт. Feetech STS3215 (КПЕ и вариометр) на общей полудуплексной UART-шине, 1 Мбит/с, 4096 шагов на оборот.
- Код прошивки: `esp32-backend/esp32-backend.ino` (Arduino, ядро esp32 3.x). Веб-страница — файлы `esp32-backend/data/` (index.html, app.js, style.css) в LittleFS; заливка по USB `tools/upload-www.sh [порт]` или через веб (сервис → «Загрузить файлы»).
- Сборка: `arduino-cli compile --fqbn esp32:esp32:esp32s3:FlashSize=16M,PSRAM=opi,CDCOnBoot=cdc esp32-backend` (`arduino-cli` лежит в `~/.local/bin`). Плата видна как `/dev/ttyACM0`.
- Старая реализация на Python (`py_server/`, `py_client/`, `common/`, Mechaduino + Raspberry Pi) — предыдущее поколение, в рамках новых задач не развивается.

## Задача 1 — веб-морда с таблицей частот

Постановка: сделать веб-морду, на которой отображается таблица для выбора частот. При выборе частоты меняется положение сервопривода. Пока всё.

Что сделано:

- Веб-страница встроена в прошивку и отдаётся с самой ESP32 (`WebServer`, порт 80).
- Таблица частот с шагом 25 кГц; выбранная частота подсвечивается. При выборе частоты оба сервопривода едут в положения из таблицы.
- Сервоприводы: ID 1 — КПЕ (`cap`), ID 2 — вариометр (`vario`). Управление по протоколу Feetech STS через `Serial1`, протокол реализован в скетче без сторонних библиотек (только запись целевого положения). При старте сервоприводы не двигаются.
- Сеть: IP только по DHCP, свою точку доступа плата не поднимает — это требование. Целевой вариант — Ethernet; пока плата T-Halow, по решению пользователя временно используется Wi-Fi-клиент; `WIFI_SSID`/`WIFI_PASS` лежат в `esp32-backend/secrets.h`, файл в `.gitignore` и не коммитится (репозиторий уходит на GitHub). Переключение — `USE_ETHERNET` в начале скетча (1 = W5500 на SPI через `ETH.h`).

## Задача 2 — режим настройки и показ одного диапазона

Постановка: на веб-странице нужен режим настройки. Выбрана частота (позже она будет приходить по CAT) — пользователь вручную «крутилками» на странице двигает сервоприводы КПЕ и вариометра, находит оптимальную настройку и сохраняет положения сервоприводов для этой частоты. На странице отображается только текущий диапазон.

Что сделано:

- Переключатель «Режим настройки» (состояние хранится на контроллере, общее для всех открытых страниц). В нём для КПЕ и вариометра — ползунок 0..4095 и кнопки шага ±1/±10/±100; сервоприводы едут сразу при изменении.
- «Сохранить» запоминает текущие положения для выбранной частоты; «Сбросить точку» удаляет сохранённую настройку (возврат к значению по умолчанию, сервоприводы не двигаются).
- Несохранённые точки берут положения линейной интерполяцией из таблицы `BANDS` (заглушка).
- Диапазоны: любительские 160–10 м плюс 100 м, 2900–3200 кГц (по просьбе пользователя, 2026-10-16).
- На странице ряд кнопок диапазонов, показаны частоты только одного; при смене частоты страница сама переходит на её диапазон. Сохранённые частоты помечены зелёной полоской.
- HTTP API (положения в шагах 0..4095):
  - `GET /api/table` — диапазоны и точки `[частота кГц, cap, vario, сохранена 0/1]`;
  - `GET /api/state` — `freq`, `cap`, `vario` (текущие, -1 пока частота не выбиралась), `tuning`, `saved`, `pcap`/`pvario` (положения из таблицы для текущей частоты);
  - `POST /api/select?freq=<кГц>` — выбрать частоту;
  - `POST /api/mode?tuning=0|1` — режим настройки;
  - `POST /api/move?cap=&vario=`, `POST /api/save`, `POST /api/reset` — только в режиме настройки и при выбранной частоте, иначе 409.

Состояние и ограничения:

- Проверено на T-Halow (2026-10-13): Wi-Fi-вариант прошит, плата получает адрес по DHCP; все методы API проверены запросами, сохранение переживает перезагрузку. Страница в браузере мной не проверялась (только синтаксис скрипта).
- Сервоприводы пока не подключены: движение, пины шины и схема согласования не проверены. `SERVO_TX_PIN`/`SERVO_RX_PIN` (IO21/IO47) выбраны по надписям гребёнки на фото; на плате они же идут на разъём камеры (камера не используется).
- Обратная связь от сервоприводов (реальное положение, ошибки) не читается.
- CAT (частота от трансивера) не реализован.
- Выбранная частота и режим настройки не сохраняются между перезагрузками. Настройки сети (Wi-Fi) задаются в `secrets.h`.
- Ethernet-вариант только собирается. Штатный RJ45 на T-Halow (V1.0 24-08-23) ESP32 недоступен: он идёт через RMII-PHY IP101GRI к HaLow-модулю TX-AH, а у ESP32-S3 нет Ethernet-MAC. Пины `ETH_*` в скетче — заглушка, уточнить под новую плату.

## Задача 3 — хранение настроек

История: сначала по просьбе пользователя настройки хранились на карте microSD (чтобы переставлять карту между платами), затем пользователь решил отказаться от карты и хранить всё во внутренней flash-памяти ESP32. Код работы с картой удалён.

Что сделано:

- Сохранённые точки лежат во flash-памяти, в NVS (`Preferences`, пространство `tubeamp`, ключ `pts`), записями «частота, КПЕ, вариометр, БМЗ». Переживают перезагрузку и обычную перепрошивку; стираются при «Erase All Flash» или смене разметки памяти.
- Перенос на другую плату — через выгрузку и загрузку таблицы: в режиме настройки под таблицей кнопки «Скачать» и «Загрузить». `GET /api/points.csv` отдаёт файл `частота;КПЕ;вариометр;БМЗ` (строки с `#` — комментарии), `POST /api/points.csv` (тело — текст файла, только в режиме настройки) заменяет все сохранённые точки; файл без единой точки отвергается.
- Точки пользователя (10 шт.) перенесены с карты во flash 2026-10-14 через загрузку таблицы.
- Попутно: вывод лога в USB не блокирует прошивку при закрытом мониторе (`Serial.setTxTimeoutMs(0)`), энергосбережение Wi-Fi выключено (`WiFi.setSleep(false)`) — оба давали задержки отклика.

## Задача 4 — переключатель БМЗ

(Привод на реле заменён третьим сервоприводом — см. задачу 7. Хранение `sw`, API и кнопки остались.)

Постановка: усилитель на базе Р-140. Кроме КПЕ и вариометра нужно переключать БМЗ на переключателе: для каждой ячейки частоты выбирается одно из положений переключателя, его тоже нужно менять в режиме настройки и сохранять.

Что сделано:

- У точки появилось положение БМЗ `sw` (1..`SWITCH_POSITIONS`, 0 — не задано). В режиме настройки на странице ряд кнопок положений; «Сохранить» без выбранного положения БМЗ отказывает.
- В записи точки и в файле таблицы четвёртый столбец — БМЗ: `частота;КПЕ;вариометр;БМЗ`. Строки без него читаются как «БМЗ не задано».
- API: в `/api/state` добавлены `sw`, `swmax`, `psw`; `POST /api/move?sw=<n>`; в `/api/table` пятый элемент точки — БМЗ.
- При выборе частоты с незаданным БМЗ все контакты размыкаются и на странице показано «не выбрано» (раньше оставалось положение предыдущей частоты — пользователь принял это за «одно положение на все ячейки»).

- Привод (уточнение пользователя): положение БМЗ выбирается замыканием одного из контактов на блоке БМЗ. В прошивке на каждое положение свой выход GPIO (`SWITCH_PINS`), активен не больше одного; при смене сначала размыкаются все, пауза `SWITCH_PAUSE_MS`, затем замыкается нужный. При старте все контакты разомкнуты, пока не выбрана частота с заданным БМЗ.

- Железо (со слов пользователя): у БМЗ 5 положений, контакты замыкает модуль реле с опторазвязкой «для Arduino». `SWITCH_PINS` = IO11..IO15 (реле 3..7 модуля, см. задачу 6).

Не сделано / открытые вопросы:

- `RELAY_ACTIVE_LEVEL = LOW` — по виду модуля (8 реле, опторазвязка, перемычка JD-VCC) такие включаются низким уровнем; на модуле пользователя не проверено.
- Нет блокировки переключения БМЗ во время передачи (сигнала PTT в прошивке нет).
- Проверено на плате (2026-10-13): выбор, отказ без БМЗ, сохранение, чтение после перезагрузки; по логу — что выбирается нужный GPIO. Модуль реле не подключён, уровни на выводах не измерялись. Страница в браузере мной не проверялась.

## Задача 5 — сервисный режим смены ID сервоприводов

Постановка: в веб-форме и прошивке сделать сервисный режим для смены ID сервоприводов.

Что сделано:

- На странице внизу раскрывающийся блок «Сервис: ID сервоприводов»: «Найти приводы» (опрос ID 0..253 с чтением положения, около 1,3 с) и «Сменить ID: с … на …».
- Прошивка научилась читать ответы приводов: `stsTransfer()` при `wantReply` ждёт ответ до `STS_REPLY_TIMEOUT_MS` (5 мс), пропускает эхо своей посылки (схема с резистором на общую линию) и проверяет контрольную сумму. Есть `stsPing()`, `stsReadPosition()` (регистр 56).
- Смена ID: проверка, что старый ID отвечает, а новый свободен; затем снятие защиты EEPROM (регистр 55 = 0), запись ID (регистр 5), защита на новом ID (55 = 1), проверка ответа на новом ID.
- API: `POST /api/servo/scan` -> `{"servos":[{"id","pos"}]}`; `POST /api/servo/id?from=&to=`.
- Команды движения ответа по-прежнему не ждут (на скорость отклика не влияет).

Проверено: на плате без приводов — опрос возвращает пустой список, смена ID отвечает понятными ошибками; разбор ответа проверен на компьютере на имитации ответов (с эхом и без, с неверной контрольной суммой). С реальными приводами не проверялось; адреса регистров взяты из протокола Feetech STS.

## Задача 6 — модуль реле: включение, прогрев, анодное, PTT

Постановка: модуль на 8 реле с опторазвязкой (входы IN1..IN8, перемычка JD-VCC) использовать для: 1) включения УМ; 2) замыкания плавного пуска через 5 с после включения, после чего все функции заблокированы 3 минуты (прогрев ламп); 3) пяти реле БМЗ (замкнуто только одно); 4) разрешения/запрета PTT (после прогрева; запрет при срабатывании защиты и отсутствии анодного); 5) включения анодного после прогрева. Веб-страница показывает процессы: этап включения, найдены ли сервоприводы, состояние PTT, анодного и т.п.

Что сделано:

- Реле (все включаются `RELAY_ACTIVE_LEVEL = LOW`): питание IO9 (реле 1), плавный пуск IO10 (реле 2), реле 3 — PTT трансивера (задача 9), реле 4..7 свободны (БМЗ теперь на сервоприводе, задача 7), PTT усилителя IO48 (реле 8, см. задачу 8), анодное IO40 — реле 1 второго модуля на 4 реле (решение пользователя; реле 2..4 этого модуля свободны).
- Входы от усилителя (`INPUT_PULLUP`, активный уровень LOW, подавление дребезга 50 мс): защита IO41, наличие анодного IO46.
- Последовательность: «Включить» -> реле питания -> через 5 с плавный пуск -> прогрев 180 с (выбор частоты и ручное управление отвечают 409) -> реле анодного -> PTT разрешается, когда есть сигнал анодного и нет защиты. «Выключить» в любой момент: PTT, анодное, плавный пуск, питание.
- PTT запрещён, пока: усилитель выключен или греется; защита сработала (защёлкивается до кнопки «Сбросить защиту», сброс возможен только при неактивном сигнале); нет сигнала анодного (первые 5 с после включения — «ожидание»); идёт поворот переключателя БМЗ или он не встал в положение (задача 7). При вращении сервоприводов PTT не снимается — настройка идёт под несущей.
- Сервоприводы опрашиваются раз в секунду (чтение положения ID 1 и 2): страница показывает реальное положение или «нет связи».
- Страница: блок состояния вверху — этап с обратным отсчётом, индикаторы (питание, плавный пуск, анодное реле/сигнал, PTT, защита, КПЕ, вариометр), причина запрета PTT, кнопки «Включить/Выключить» (с подтверждением) и «Сбросить защиту». Во время прогрева таблица и ручное управление неактивны.
- API: `POST /api/power?on=0|1`, `POST /api/protection/reset`; в `/api/state` поля `amp` (off/softstart/warmup/ready), `remain`, `power`, `soft`, `anode`, `anodeOk`, `protect`, `protectLatched`, `ptt`, `pttReason`, `servoCap`, `servoVario`.
- После перезагрузки ESP32 все реле выключены, усилитель выключается.
- Вёрстка (по просьбе пользователя): кнопка «Включить/Выключить» слева в блоке состояния; на компьютере (от 900 px) две колонки — слева состояние и режим настройки, справа таблица частот; на телефоне (до 600 px) одна колонка: состояние, таблица, настройка, сервис; крупные кнопки под палец. Проверено снимками headless Chrome с платы (1400 px и 390 px).

Открытые вопросы к пользователю:

- Как устроены сигналы защиты и наличия анодного (контакт, оптрон, уровень) — сейчас предположение: замыкание на GND = активен.
- Что делать с анодным при срабатывании защиты (сейчас остаётся включённым, снимается только PTT).
- Пины на T-Halow почти исчерпаны; IO46 — strapping-пин (как вход допустим), IO40/IO41 раньше шли на слот SD (карту лучше вынуть). IO9..IO14 конфликтуют с W5500 при `USE_ETHERNET 1` — на новой плате всё переназначить.

## Задача 7 — переключатель БМЗ на третьем сервоприводе

Постановка: БМЗ на реле больше нет, вместо него третий сервопривод вращает переключатель. Шаг 360/5 — 5 положений; ограничителей нет, вращение в любую сторону, кратчайшим путём или по кругу. Положение выбирается кнопками на странице и сохраняется для частоты, прошивка сама ставит привод в одно из 5 положений.

Решения пользователя: ID привода 3; калибровка положения 1 через веб; PTT снимается на всё время поворота.

Что сделано:

- Привод ID 3 переводится в шаговый режим STS (регистр 33 = 3, запись в EEPROM только если режим другой). Положение n -> шаг `switchOffset + (n-1)*4096/5` (0, 819, 1638, 2458, 3277 + смещение). Перед поворотом читается текущее положение (с декодированием знака в 15-м бите и приведением к 0..4095), считается кратчайшая разница ±2048 и отправляется относительное перемещение — ошибка не накапливается.
- Поворот неблокирующий: `updateSwitch()` раз в 50 мс читает положение; встал (допуск 20 шагов) — PTT возвращается; нет за 4 с или привод не отвечает — `switchFailed`, PTT запрещён до успешного поворота.
- Калибровка в сервисном блоке: кнопки ±1/±10/±100 (`POST /api/switch/jog?steps=`) и «Запомнить как положение 1» (`POST /api/switch/calibrate`); смещение в NVS, ключ `swofs`.
- Страница: индикатор «Переключатель» (положение / поворот / не встал / нет связи); в `/api/state` поля `servoSwitch`, `swMoving`, `swFailed`, `swOffset`.
- Реле 3..7 (IO11..IO15) освобождены. Лямбда в `sendState()` заменена функцией `jsonBool()` (правило пользователя: без лямбд в C++).

Проверено: математика положений и кратчайшего пути — на компьютере; на плате без привода — понятные ошибки, PTT блокируется. С реальным приводом не проверялось: шаговый режим, формат положения в нём и направление вращения требуют проверки.

## Задача 8 — PTT через ESP32 и охлаждение перед выключением

Постановка: управление PTT завести в ESP32 и учесть таймаут после последней передачи в эфир. Если выбрали «Выключить», а с последней передачи прошло меньше 5 минут, усилитель не выключается, но показывается кнопка «Выключить без охлаждения».

Что сделано:

- PTT трансивера — вход IO11 (`INPUT_PULLUP`, активен LOW, дребезг 5 мс). Реле 8 теперь «PTT усилителя»: замкнуто, пока вход PTT активен и `pttBlockReason()` пуст (прогрев окончен, есть анодное, нет защиты, переключатель БМЗ встал).
- Последняя передача — последний момент, когда реле 8 было замкнуто (`lastTxMs`, `txHappened`); после перезагрузки ESP32 считается, что передачи не было.
- `POST /api/power?on=0` при `cooldownSeconds() > 0` (меньше `COOLDOWN_MS` = 5 мин с передачи) отвечает 409; `&force=1` выключает сразу. Страница после отказа показывает кнопку «Выключить без охлаждения» и отсчёт охлаждения.
- Вариант, когда при «Выключить» во время охлаждения снимается анодное и усилитель выключается сам по окончании, предлагался; пользователь на вопрос не ответил, сделано по его постановке (просто не выключать).
- `/api/state`: `ptt` (реле 8 замкнуто), `pttAllowed`, `pttReason`, `txReq` (вход PTT), `lastTx` (секунд с передачи, -1 — не было), `cooldown` (секунд до конца охлаждения).
- Задержка PTT: цикл прошивки при отсутствующих приводах занят опросом до ~15 мс раз в секунду, плюс 5 мс дребезга и время срабатывания реле — задержку передачи на трансивере лучше выставить с запасом.

Проверено: на плате — поля состояния и выключение без передачи; логика замыкания PTT и отсчёта охлаждения — на компьютере с имитацией времени. Вход PTT и реле на железе не проверялись.

## Задача 9 — страница во flash, передача с веб-страницы, отладочные таймауты

Постановка: хранить веб-страницу не в программе, а во flash и отдавать оттуда (план целиком: файлы, запасная страница, скрипт заливки, загрузка через веб, сверка версий); добавить на страницу клавишу перевода трансивера на передачу; для отладки сократить таймауты включения и выключения до 10 с (в усилителе вернуть).

Что сделано:

- Страница разнесена на `esp32-backend/data/index.html`, `app.js`, `style.css`; прошивка отдаёт их из LittleFS (раздел `spiffs` таблицы default.csv: 0x290000, 0x160000), `Cache-Control: no-cache`. Если `index.html` нет — встроенная запасная страница `FALLBACK_HTML` с формой загрузки.
- `POST /api/www` (multipart): имена только `[A-Za-z0-9._-]`, расширения html/js/css/svg/png/ico; запись через `.tmp` с подменой. На странице в сервисе — «Загрузить файлы».
- `tools/upload-www.sh [порт]`: `mklittlefs` (-p 256 -b 4096) + `esptool write-flash 0x290000`. NVS (точки, калибровка) не затрагивается.
- Версия: `WWW_API_VERSION` в прошивке и `API_VERSION` в app.js, поле `api` в `/api/state`; при расхождении — красная плашка. Менять оба числа при несовместимом изменении API.
- Передача с веб-страницы: реле 3 модуля на 8 реле, IO12 (`RELAY_TRX_PTT_PIN`) — замыкает PTT трансивера. `POST /api/tx?on=1` начать, `?keep=1` подтверждение (страница шлёт каждые 0,5 с), `?on=0` закончить; без подтверждения 2 с (`WEB_TX_KEEPALIVE_MS`) или через 60 с (`WEB_TX_MAX_MS`) снимается сама; при выключении усилителя снимается. Трансивер, уйдя на передачу, сам даёт PTT на IO11 — дальше обычная логика PTT усилителя. Выбор кнопка-переключатель + сторожевой таймер (а не «держать нажатой») — мой: при настройке под несущей нужны свободные руки для ползунков.
- ОТЛАДКА: `WARMUP_MS = 10000` (было 180000), `COOLDOWN_MS = 10000` (было 300000). Перед работой с усилителем вернуть.

Проверено на плате (2026-10-16): запасная страница без файлов, загрузка через веб (в т.ч. отказ на `../evil.html`), раздача файлов байт в байт, скрипт по USB, точки после заливки на месте, передача с веб-страницы (старт, подтверждения, автоснятие без подтверждения, стоп), прогрев 10 с. Реле 3 на железе не проверялось.

## Справка: HaLow-модуль TX-AH на T-Halow

Разобрано по примерам и документации LilyGO (github.com/Xinyuan-LilyGO/T-Halow), на железе не проверялось. В проекте пока не используется.

- У TX-AH две взаимоисключающие прошивки (на съёмной микросхеме Flash):
  - `...-usb.bin` — режим AT: ESP32 управляет модулем по UART (`Serial1`, 115200, RX = GPIO4, TX = GPIO5) и обменивается данными с парной платой по радио;
  - `...-WNB.bin` — сетевой мост RJ45 <-> HaLow <-> RJ45; настраивается по micro-USB, ESP32 в обмене не участвует.
- Отправка: `AT+TXDATA=<длина>`, дождаться `OK`, затем послать ровно `<длина>` байт: 14 байт Ethernet-заголовка (MAC получателя, MAC отправителя, тип) + полезные данные.
- Приём: модуль выдаёт строку `+RXDATA:...`, после перевода строки — тот же кадр (14 байт заголовка + данные). Пример `TX_AH_Rx00p_STA` пропускает 15 символов после начала перевода строки.
- Состояние связи: `AT+CONN_STATE` -> `+CONNECTED` / `+DISCONNECT`; уровень сигнала: `AT+RSSI=1`.
- Сопряжение: одна плата AP, другая STA (`AT+MODE=AP|STA` или переключатель на плате), затем `AT+PAIR=1` на обеих или кнопка PAIR.
- Занятые на плате GPIO: 4/5 — UART к TX-AH, 39/40/41/42 — SD-карта, 38 — светодиод, 6/7 — I2C.
